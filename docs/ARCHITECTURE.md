# Архитектура YORVI — целевое состояние

> Это **план**, а не описание уже развернутой инфраструктуры. Версия 1.4 — браузерный React/TypeScript прототип с localStorage.

## Компоненты
- **Frontend:** React + TypeScript, предпочтительно Vite, адаптивный Mini App/web интерфейс.
- **Backend:** Node.js + Fastify (или аналог с TypeScript), REST API, схемы валидации.
- **БД:** PostgreSQL с миграциями.
- **Фотографии:** S3-совместимое объектное хранилище, ресайз, лимиты, проверка содержимого.
- **MAX:** бот и Mini App; подпись данных входа проверяется **на сервере** по актуальной документации MAX; поддерживаемые сценарии публикации — только после проверки API.
- **Эксплуатация:** HTTPS, логи, метрики, резервное копирование, CI/CD, секреты вне репозитория.

## Модель данных (основные таблицы)
- `users` — пользователь, учётная запись MAX (если доступна), состояние, даты.
- `communities` — круг, владелец, правила, статус.
- `community_members` — членство и роль.
- `listings` — единая карточка, автор, категория, цена, **глобальный статус**.
- `listing_media` — файлы, порядок, alt-тексты и метаданные.
- `listing_placements` — запись объявления в круге, **отдельный статус модерации**.
- `moderation_actions` — модератор, решение, причина, время, аудит.
- `favorites` — связь пользователь/объявление.
- `reports` — жалобы, причины и решения.
- `events` — события домена и идемпотентная обработка.

## Глобальные статусы объявления
`draft -> pending -> active -> reserved -> sold`, дополнительно `archived`/`blocked`; точная машина состояний уточняется при реализации. При статусе `sold`, `archived` или `blocked` карточка должна пропадать из активных выдач **во всех кругах** независимо от модерации.

## Статусы размещения
Для каждой пары `(listing_id, community_id)` ровно одно активное размещение; `pending | approved | rejected | removed`. Одобрение в круге A **не** даёт одобрения в B.

### Инварианты
- `UNIQUE(listing_id, community_id)` на уровне БД.
- Нельзя публиковать заблокированный, архивный или проданный лот.
- Редактирование существенных полей может требовать повторной модерации конкретного размещения.
- Только владелец редактирует лот; только уполномоченный модератор принимает решение по своему кругу.
- Админ-панель не должна полагаться на скрытие кнопок как на защиту прав.

## Защита от дублей
Идемпотентный ключ запроса на создание объявления, уникальные размещения, серверная нормализация названия, предупреждение о похожих лотах по автору/фотографиям, ограничение частоты публикации. Не использовать один лишь perceptual hash как автоматическое основание блокировки.

## Минимальные API
- `GET /listings`, `GET /listings/:id`
- `POST /listings`, `PATCH /listings/:id`
- `POST /listings/:id/placements`
- `POST /placements/:id/approve`, `POST /placements/:id/reject`
- `POST /listings/:id/sold`
- `GET /communities`, `GET /communities/:id/listings`
- `POST /media/presign`
- `POST /reports`
- `POST /auth/max` (только после проверки формата SDK/API)

## Безопасность
Проверка всех прав на сервере, серверная валидация, rate limiting, защита от повторов вебхуков, контроль доступа к медиа, секреты в env, аудит модерации, резервные копии, удаление персональных данных согласно применимым требованиям.

## Ограничения прототипа 1.4
Данные живут в localStorage; реальной БД, MAX API, защищённых ролей и платежей нет; React 16 UMD устарел и не подходит для production.
