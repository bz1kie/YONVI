## 1. Развернуть HTTPS

Для существующего React/Fastify/PostgreSQL добавлен готовый шаблон Docker Compose + Caddy: [развёртывание YONVI на VPS](PRODUCTION_VPS.md). Домен и VPS пока не настроены.

Разместить frontend и backend под **одним HTTPS origin** (например, `https://<ваш-домен>`):
- `/` → собранный `apps/web/dist` (Vite/React);
- `/api/*` → Fastify (локально порт `3001`);
- `/health` → Fastify для технической проверки.

Важно: прокси `/api` в `apps/web/vite.config.ts` работает **только локально** во время разработки. В production нужен реальный HTTPS reverse proxy или эквивалентный маршрутизатор.

Не подключать Mini App к MAX, пока не развернуты и не проверены backend, PostgreSQL и SSL. Фотографии дополнительно требуют закрытого S3-совместимого хранилища с HTTPS и правильно настроенным CORS.

## 2. Настроить секрет только на API-сервере

В настройках окружения сервера/контейнера API задать:

```dotenv
NODE_ENV=production
ALLOW_DEMO_AUTH=false
DATABASE_URL=postgresql://<user>:<password>@<host>:5432/<database>
WEB_ORIGIN=https://<ваш-домен>
MAX_YONVI_TOKEN=<ваш-реальный-токен-MAX>
```

Приложение поддерживает либо `MAX_YONVI_TOKEN`, либо прежний `MAX_BOT_TOKEN`. Если заданы оба, приоритет у `MAX_BOT_TOKEN`. Удалите устаревшую переменную при миграции, чтобы случайно не использовать неправильного бота.

GitHub repository secret `MAX_YONVI_TOKEN` **не поступает автоматически на production-сервер**. Только явный deployment workflow/секретное хранилище хостинга может безопасно передать его. `.github/workflows/ci.yml` — тестовый workflow; `.github/workflows/render.yml` выполняет развёртывание и передаёт секрет в Render. Не нужно подключать боевой токен к тестам или pull_request CI.

Запрещено добавлять токен в репозиторий, `VITE_*` переменные, страницы, скриншоты и публичные логи. Не включайте `ALLOW_DEMO_AUTH=true` в публичном окружении.

## 3. Проверить API и вход

1. Открыть `https://<ваш-домен>/` и убедиться, что загружается каталог.
2. Проверить `GET https://<ваш-домен>/health`: ответ должен быть `{"ok":true,...}`.
3. Проверить `GET https://<ваш-домен>/api/auth/me` вне MAX: для гостя ожидается `401`.
4. Внутри MAX после реального открытия приложения компонент авторизации должен получить подписанный `initData`, отправить POST `/api/auth/max` и создать cookie-сессию. Без реального запуска в MAX этот шаг нельзя считать проверенным.
5. Проверить каталог, сохранение объявления, круги, обновление фотографии и права нескольких разных пользователей.

## 4. Привязать URL в MAX

По актуальной документации MAX:
1. Открыть [MAX для партнёров](https://business.max.ru/) → **Чат-боты**.
2. Выбрать бота **YONVI | Объявления** → **⋮ → Настройки**.
3. Вставить **реальный HTTPS URL** запущенного приложения.
4. Выбрать кнопку открытия **«Открыть»** и сохранить.

Требования MAX: HTTPS, валидный адрес длиной до 1024 символов. После сохранения в чате с ботом появится кнопка запуска Mini App.

Для внешнего открытия после привязки поддерживается формат `https://max.ru/<botName>?startapp`. Не публиковать его как рабочий, пока URL Mini App не привязан и не проверен.

## 6. Разделение ответственности

- **GitHub** — исходники, CI и при необходимости будущий деплой; хранение секретов только в GitHub Secrets.
- **Хостинг** — HTTPS, API, база и серверное хранение действующего токена.
- **MAX для партнёров** — регистрация бота и привязка HTTPS-адреса Mini App.

Сначала требуется выбрать и развернуть хостинг. Сам факт наличия GitHub Secret не запускает Mini App.
